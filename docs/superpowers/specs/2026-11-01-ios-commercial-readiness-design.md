# iOS 사내 실무 적용 설계

2026-11-01 · 사용자 검토 대기 · 대상 브랜치 `feature/ios-commercial-readiness`

## 1. 의도와 이유

회사 사람들이 **자사 iOS 앱**에서 이 흐름을 실무로 돌릴 수 있게 한다.

1. QA가 버그를 녹화한다.
2. 개발자가 그 녹화로 같은 버그를 재현한다.
3. Claude가 수정안을 만들고, 같은 녹화로 다시 돌려 고쳐졌는지 검증한다.

판매용 제품이 아니라 **사내 실사용**이 목표다. 지금 Reproof는 번들 샘플과
명시적으로 프로필을 손으로 쓴 UIKit 앱에서만 이 흐름이 끝까지 동작한다. 실무
앱에 붙이지 못하는 이유는 네 가지다.

- 자사 앱은 **SwiftUI와 UIKit을 섞어 쓴다.** 현재 녹화·자동 관찰은 UIKit
  `UIControl`의 `sendAction` 경로만 본다.
- 자사 앱의 버튼·입력창 대부분에 **테스트용 ID(`accessibilityIdentifier`)가 없다.**
  현재 재생·판정·locator 제안은 ID를 전제로 한다.
- 자사 앱은 **외부 SPM 패키지와 수천 개 파일**을 쓴다. 현재 iOS 준비 단계는
  외부 패키지를 받지 않고 입력을 900개·60 MiB로 제한한다.
- **설정이 복잡하고 승인 단계가 많다.** 사용자가 "이건 못 쓰겠다"고 명시한
  지점이다. 현재는 JSON 프로필 손작성, revision·digest 승인, 고정 해시 pin,
  qualification 등을 사람이 직접 다룬다.

Android(Compose+Views 혼용)는 이 설계의 범위가 아니다. iOS를 끝까지 완성한 뒤
같은 방식으로 별도 설계한다.

## 2. 사용자와 장면

- **QA**는 두 방식 모두로 녹화할 수 있어야 한다(사용자 결정).
  - 손에 든 iPhone 또는 Mac의 Simulator를 **직접 터치**한다.
  - 브라우저 Live 콘솔로 기기를 **원격 조작**한다.
  - 녹화를 끝내면 녹화 화면에서 "버그가 보이는 요소"를 골라 실제 상태와 기대
    상태를 지정하고 저장한다.
- **QA의 Mac에는 회사 앱 소스와 Xcode가 없다. QA는 빌드만 받아서 쓴다**(사용자 결정).
  그래서 QA Mac에서는 Simulator도, `devicectl`을 통한 iPhone 설치도 쓸 수 없다.
  QA의 두 녹화 방식은 다음 경로로 성립한다(설계자 판단, 6장 "QA 녹화용 빌드 배포").
  - 원격 조작: 브라우저로 공유 모드의 공용 Mac에 있는 Simulator나 iPhone을 조작한다.
  - 직접 터치: 개발자나 CI가 배포한 녹화용 빌드를 QA 자기 iPhone에 설치해 쓴다.
    공용 Mac에 꽂힌 iPhone을 그 자리에서 직접 만질 수도 있다.
- **개발자**는 저장된 이슈를 열어 "재현"을 실행해 원본 빌드에서 반복 재현을
  확인하고, "AI 수정"을 실행해 검증된 수정안(diff)을 받는다. diff를 자기 브랜치에
  적용할지는 개발자가 정한다.
- **사용 형태는 두 가지 모두다**(사용자 결정).
  - 각자 자기 Mac에서 쓰는 **로컬 모드**.
  - 기기가 연결된 공용 Mac(들)을 여러 명이 같이 쓰는 **공유 모드**. 기존 공유
    coordinator·역할·호스트 등록을 사용한다.
- 회사는 자사 앱 소스를 **Claude에 보내는 것을 허용한다**(사용자 결정). 다른 외부
  AI는 이 설계에서 쓰지 않는다.
- 회사 소스는 개발 과정에 제공되지 않는다(사용자 결정). 검증은 공개 대규모 앱으로
  한다(5장).

## 3. 목표

1. **설정 한 번.** `reproof init`(이름은 빌더 재량)이 앱 프로젝트를 훑어
   `.xcodeproj`/`.xcworkspace`, scheme, 앱 타깃, bundle id, SPM 의존성, 테스트
   타깃, 사용할 Simulator/iPhone을 자동으로 찾는다. 사람이 읽고 고칠 수 있는 작은
   설정 파일을 만든다. 모호할 때만 짧게 묻는다. 환경 문제는 원인과 해결 명령을 함께
   보여 준다.
2. **SwiftUI·UIKit 혼용 화면 녹화.** 순수 SwiftUI 화면, 순수 UIKit 화면,
   `UIHostingController`로 UIKit 안에 끼운 SwiftUI 화면 모두. 직접 터치와 브라우저
   원격 조작 둘 다.
3. **ID 없는 요소의 안정적 식별.** 녹화·재생 전용 Debug 빌드에서 자동 ID를 부여하고,
   그래도 못 찾는 요소는 대체 locator로 찾되 결과에 "약한 근거"로 표시한다
   (6장 결정 참고).
4. **판정 기준을 화면에서 지정.** QA가 녹화된 화면에서 요소를 고르고 속성(존재 여부,
   label, value, enabled/selected)을 실제값·기대값으로 지정한다. 앱 크래시는 별도
   설정 없이 결함 조건으로 쓸 수 있다.
5. **반복 재현.** 원본 빌드에서 같은 녹화를 기본 3회 실행해 3회 모두 결함이면
   `reproduced`.
6. **대규모 소스의 AI 수정 검증.** Claude가 전체 앱 소스를 보고 수정안을 만든다.
   후보 빌드에서 같은 녹화를 3회 실행해 3회 모두 정상이고, 지정된 기존 테스트가
   통과하면 `verified`. 섞이면 `inconclusive`.
7. **승인 단계 축소.** 간편 모드를 기본값으로 한다(4장 반목표 기준).
8. **로컬·공유 모드 동일 흐름.** 같은 이슈 형식과 같은 판정을 쓴다.
9. **공개 대규모 앱으로 끝까지 검증.** 5장의 수용 기준을 실제 실행 증거로 통과한다.

## 4. 비목표와 반목표

### 비목표

- Android, Flutter, React Native, 웹뷰 내부 DOM 요소, 게임 엔진 화면.
- 앱 내부의 모든 비동기 함수·HTTP·DB 호출 자동 계측.
- 서버 응답 녹화·재생(네트워크 stub). 시작 조건은 6장의 방식으로만 다룬다.
- Release·App Store 빌드 변경. Release에는 런타임·자동 ID·hook을 넣지 않는다.
- 판매용 기능(과금, 멀티테넌시, 외부 SaaS 호스팅).
- 영상만 보고 AI가 입력을 추측해 재생 가능한 기록으로 만드는 기능.
- 기존 엄격 모드(고정 pin, qualification, 격리 VM 경로, Android 복구 qualification)의
  개선. 그대로 옵션으로 유지한다.
- 회사 저장소에 대한 자동 commit·push·PR 생성.

### 반목표 — 기술적으로 돌아가도 실패로 본다

- 설정에 사람이 JSON·해시·긴 경로·digest를 여러 개 손으로 써야 한다.
- 간편 모드에서 녹화부터 검증까지 사람의 승인·확인이 아래보다 많다.
  - QA: 녹화 종료 후 버그 지점 지정과 저장, 1회.
  - 개발자: "재현"과 "AI 수정" 실행, 마지막 diff 채택 판단, 1회.
  - 프로젝트당 1회: 초기 설정과 "이 프로젝트 소스를 Claude에 보내는 데 동의".
- 내부 검사가 실패했을 때 해시·내부 용어만 보이고 원인과 해결 방법이 없다.
- 성공한 실행만 골라 `reproduced`/`verified`로 표시한다.
- AI 수정안이 테스트·판정 기준·녹화·빌드 설정·프로젝트 파일을 바꿔서 통과한다.
- 회사 원본 소스나 사용자의 기존 Simulator·iPhone 앱 데이터를 덮어쓰거나 지운다.
- 회사 소스가 Claude 이외의 곳으로 전송된다.

## 5. 수용 기준과 검증 앱

### 검증 앱

**Wikipedia iOS**(`wikimedia/wikipedia-ios`, MIT)를 쓴다. 2026-11-01 GitHub 조회
결과는 다음과 같다.

- 파일 약 4,720개, Swift 1,522개, Objective-C `.m` 208개.
- `UIHostingController`로 UIKit 안에 SwiftUI를 끼운 화면이 다수다.
- 로컬 SPM 패키지 4개(`WMFComponents`, `WMFData` 등)와 외부 SPM 의존성
  (CocoaLumberjack, SDWebImage, RxSwift 등)을 쓴다.
- `accessibilityIdentifier`를 쓰는 파일이 약 91개로, 대부분 요소에 ID가 없다.

회사 앱과 구조가 비슷하다. 특정 commit SHA로 고정하고, Wikipedia 소스는 Reproof
저장소에 넣지 않는다. Reproof 저장소에는 고정 SHA, 내려받기 스크립트, 심은 버그
patch만 둔다. 앱 빌드에 필요한 Xcode 최소 버전은 16이고 이 Mac에는 Xcode 27이 있다.

심은 버그는 최소 세 개다.

- 순수 SwiftUI 화면의 로직 버그 1개.
- 순수 UIKit 화면의 로직 버그 1개.
- UIKit 안에 끼운 SwiftUI 화면의 버그 1개.

네트워크 응답에 좌우되지 않는 화면(설정·온보딩·로컬 상태 화면 등)을 우선 고른다.
구체적인 화면·버그는 빌더가 정한다.

### 수용 기준 — 모두 실제 실행 증거로

1. 새 가상 환경에 wheel을 설치하고 `init`부터 시작한다. 고정 SHA의 Wikipedia에서
   설정이 끝날 때까지 사람이 직접 입력한 항목 수와 걸린 시간을 기록한다. 목표는
   Xcode 빌드 시간을 빼고 10분 이내, 직접 입력 3개 이하.
2. 세 버그 각각에 대해 다음을 끝까지 통과한다.
   1. 녹화한다. 버그마다 직접 터치와 브라우저 원격 조작 중 하나를 쓰되, 세 버그
      전체에서 두 방식이 모두 한 번 이상 쓰여야 한다.
      - 직접 터치는 Simulator 창에서 실제 마우스 입력으로 한다. 앱 안의 터치 기록
        경로는 기기와 같다.
      - 원격 조작은 Xcode가 없는 QA 역할 사용자가 브라우저로 공유 모드에 접속해서 한다.
   2. 버그 지점을 지정한다.
   3. 원본 3/3 `reproduced`를 받는다.
   4. 실제 Claude로 수정한다.
   5. 후보 3/3 정상과 지정 테스트 통과로 `verified`를 받는다.
3. 반례도 실제로 확인한다.
   - 테스트나 판정을 바꾸는 후보는 거절된다.
   - 위험 API(6장 "후보 자동 위험 검사")를 새로 넣은 후보는 실행 전에 거절된다.
   - 결과가 섞인 실행은 `inconclusive`가 된다.
   - 원본에서 재현되지 않는 녹화는 `reproduced`가 되지 않는다.
4. 간편 모드의 사람 승인·확인 횟수가 4장 기준 이하다.
5. 로컬 모드와, 같은 Mac에서 coordinator와 worker 프로세스를 따로 띄운 공유 모드에서
   같은 이슈가 같은 판정을 낸다.
6. **회사 앱 빌드 요소.** 회사 앱은 Tuist/XcodeGen 생성 프로젝트와 비공개 SPM
   저장소를 쓴다(사용자 답). Wikipedia는 둘 다 쓰지 않으므로 별도 검증용 앱으로 확인한다.
   - **XcodeGen:** 이 Mac에 `/opt/homebrew/bin/xcodegen`이 있다. SwiftUI+UIKit 혼용
     합성 앱을 `project.yml`로 만들고, `init`부터 `verified`까지 버그 1개를 통과한다.
   - **비공개 SPM:** 인증이 필요한 loopback git 서버에 올린 합성 패키지를 위 앱이
     쓰게 한다. 개발자의 기존 git 인증 방식(credential helper/SSH 설정)으로 받아지는지
     확인한다. 툴이 인증 값을 직접 읽거나 저장하지 않는다. 검증용 인증은 임시
     HOME에 만든 테스트 전용 값만 쓰고, 사용자의 실제 키·keychain은 건드리지 않는다.
   - **Tuist:** 이 Mac에 설치돼 있지 않고 설치 승인도 없다. 지원 코드는 만들되
     실제 실행 검증은 설치 승인 뒤로 미루고, 결과에 "미검증"으로 표시한다.
7. **물리 iPhone 수용은 미룬다.** 이번 승인 범위에 물리 iPhone 사용이 없다(사용자 답).
   iPhone 경로(배포 빌드 서명, 기기 설치, 앱 안 녹화 업로드)는 구현하고 portable
   검사로 확인하되, 실기기 실행은 사용자가 기기를 승인할 때까지 "미검증"으로 남긴다.
   Simulator 결과로 iPhone 지원을 완료라고 표시하지 않는다.
8. 기존 portable 검사·CI가 계속 통과하고, 엄격 모드의 기존 동작과 검사가 바뀌지
   않는다.

## 6. 정해진 방식

여기서 **사용자 결정**은 대화에서 사용자가 정한 것이고, **설계자 판단**은 사용자가
위임해 이 문서 작성자가 정한 것이다.

### 기존 구조 위에 짓는다 (설계자 판단)

- Python 호스트(런타임은 표준 라이브러리만, `dependencies = []` 유지), Debug
  빌드에 주입하는 Objective-C bootstrap + Swift 런타임, XCUITest 기반 재생
  runner, Live 콘솔과 공유 coordinator, G7 이슈 흐름, G9 수정 제안 경로를 확장한다.
  새로 갈아엎지 않는다.
- 간편 모드는 기존 부품을 재사용하는 **새 기본 경로**다. 엄격 모드의 코드·검사·
  문서는 지우거나 약하게 바꾸지 않는다.
- 사용자에게 보이는 문구와 오류는 한국어를 기본으로 한다. 오류에는 원인과 해결
  방법을 넣는다.

### 요소 식별 (사용자 결정 + 설계자 판단)

- **사용자 결정:** 녹화용 Debug 빌드에서만 ID를 자동으로 붙이고, 회사 원본 소스와
  Release는 건드리지 않는다. 못 찾는 요소는 대체 방식으로 찾되 "약한 근거"로
  표시한다. 좌표만으로 재생하는 방식은 쓰지 않는다.
- **설계자 판단 — locator는 여러 근거를 함께 저장한다:**
  1. 앱이 원래 붙인 `accessibilityIdentifier`.
  2. 자동 ID.
  3. 요소 종류 + label + 가장 가까운 ID 있는 조상.
  4. 같은 조건 안의 순번.

  재생은 위 순서로 찾는다. 어느 근거로 찾았는지 실행마다 기록하고, 3·4로 찾은
  결과는 리포트에 "약한 근거"로 따로 센다. 좌표는 기록에 남기되 요소를 찾는
  근거로는 쓰지 않는다.
- **설계자 판단 — 자동 ID 방식:**
  - UIKit은 런타임에 붙인다. 화면 전환 시 view controller의 프로퍼티 이름 등을 써서
    `SettingsViewController.saveButton`처럼 의미 있고 안정적인 ID를 붙인다.
  - SwiftUI는 런타임에서 안정적인 ID를 얻기 어렵다. 빌더가 먼저 아래 spike로
    정한다.
- **AI 수정 뒤에도 ID가 유지돼야 한다.** 후보 소스에서 줄 번호가 바뀌어도 같은
  요소는 같은 ID를 가져야 한다. 줄 번호 기반 ID는 쓰지 않는다.
- **결정성:** 툴이 직접 만든 전용 Simulator(이름에 `reproof-` 접두사)에서 실행한다.
  로케일·지역·시간대·텍스트 크기를 고정하고, 매 실행 전에 초기화 후 새로 설치한다.
  사용자가 원래 쓰던 Simulator와 기기 데이터는 건드리지 않는다.

### 녹화 (사용자 결정 + 설계자 판단)

- **사용자 결정:** 직접 터치와 브라우저 원격 조작 둘 다 지원한다.
- **원격 조작:** 툴이 모든 입력을 XCUITest로 넣는다. 입력 직전에 그 좌표의 접근성
  요소를 조회해 locator를 만든다. SwiftUI와 UIKit 모두 같은 방식이다.
- **직접 터치:** Debug 런타임이 앱 안에서 터치를 기록한다(`UIApplication.sendEvent`
  관찰). UIKit은 hit-test로 대상 view를 찾는다. SwiftUI 요소를 앱 안에서 찾을 수
  있는지는 spike로 확인한다.
- **직접 터치의 대안:** 앱 안에서 SwiftUI 요소를 못 찾으면, 녹화 직후 툴이 같은
  시작 조건에서 녹화를 한 번 다시 돌린다. 각 단계 직전에 XCUITest로 그 좌표의 요소를
  조회해 locator로 바꾼다. 이 "변환 실행"이 원본 화면과 다르게 흘러가면 그 녹화는
  재현 불가로 남기고 조용히 고치지 않는다.
- 텍스트 입력은 완료된 값을 기록한다. 비밀번호·토큰은 저장하지 않고, 기존 변수
  참조 방식(환경 변수로 실행 시 공급)으로 바꾼다.

### 시작 조건 (설계자 판단)

- 기본은 깨끗한 새 설치다.
- 설정 파일에서 launch arguments와 환경 변수(비밀값은 환경 변수 참조로)를
  선언할 수 있다.
- 로그인처럼 반복되는 준비 과정은 별도의 "준비 녹화"로 저장하고 여러 이슈가 재사용할
  수 있다.
- 서버 데이터에 좌우되는 버그는 반복 재현에서 결과가 섞여 `inconclusive`로 드러나게
  두고, 숨기지 않는다.

### 판정 (설계자 판단)

- 마지막 동작 뒤 접근성 스냅샷에서, 저장된 locator로 요소를 찾아 지정 속성을
  비교한다.
- 크래시는 기본 결함 조건으로 쓸 수 있다.
- 스크린샷 픽셀 비교는 기본 판정에 쓰지 않는다. 애니메이션·폰트 때문에 흔들린다.

### 빌드 (설계자 판단)

- `.xcworkspace`, SPM(로컬·외부 패키지)을 지원한다.
- **Tuist/XcodeGen 생성 프로젝트를 지원한다(우선순위 높음, 사용자 답).**
  - `init`이 `project.yml`(XcodeGen)이나 `Project.swift`·`Tuist/`(Tuist)를 찾으면,
    매 빌드 전에 작업 사본에서 생성기를 실행해 프로젝트를 만든다.
  - 생성된 `.xcodeproj`는 산출물로 취급한다.
  - 생성기 manifest(`project.yml`, `Project.swift`, `Tuist/` 등)는 AI 수정 범위 밖이다.
- **비공개 SPM 저장소를 지원한다(우선순위 높음, 사용자 답).**
  - 의존성 해석은 개발자 Mac의 기존 git 인증(credential helper, SSH 설정)을 그대로 쓴다.
  - 툴은 인증 값을 읽거나 복사하거나 이슈·리포트·Claude 요청에 넣지 않는다.
  - 인증 실패는 "어느 저장소 URL에서 인증이 실패했는지"와 해결 방향만 보여 준다.
- CocoaPods는 회사 앱이 쓰지 않으므로(사용자 답) 이번 범위에서 뺀다.
- 의존성은 `init`이나 준비 단계에서 한 번 받아 캐시한다. 원본·후보 빌드는 같은
  캐시를 써서 의존성 차이가 결과를 바꾸지 않게 한다.
- 파일 900개·60 MiB 한도는 간편 모드에서 실무 규모(Wikipedia 전체)에 맞게 바꾼다.
  엄격 모드의 한도는 그대로 둔다.
- 서명:
  - Simulator는 서명이 필요 없다.
  - 물리 iPhone은 개발자가 이미 쓰는 Xcode 자동 서명과 team ID를 `init` 때 한 번
    받아서 쓴다. 기존 고정 서명 도구 경로는 엄격 모드 전용이다.

### AI 수정 (사용자 결정 + 설계자 판단)

- **사용자 결정:** Claude를 쓴다. 회사 소스 전송이 허용된다.
- **설계자 판단 — Claude CLI는 앱 소스의 별도 작업 사본에서 실행한다.** 전체 소스를
  읽을 수 있고, 다음 자료를 함께 받는다.
  - 녹화 단계(locator 포함). 자동 ID가 있으면 해당 소스 위치 힌트도 준다.
  - 판정 기준과 원본 실행의 실패 관측.
  - 크래시 로그.
- **수정 범위:** 앱 제품 소스(Swift/Objective-C)만 바꿀 수 있다. 아래 파일을
  바꾼 후보는 빌드 전에 거절한다.
  - 테스트 타깃.
  - 녹화·판정 기준.
  - `.pbxproj`·`Package.swift`·`Package.resolved`·xcconfig·build phase 스크립트.
  - Tuist/XcodeGen manifest(`project.yml`, `Project.swift`, `Tuist/` 등).
  - entitlements·Info.plist.
- **후보 빌드는 개발자 Mac에서 직접 빌드한다(host build).** 리포트에 "호스트 빌드"로
  표시하고 "격리 빌드"로 표시하지 않는다. 격리 VM 경로는 엄격 모드 옵션으로 남는다.
  AI가 프로젝트·패키지·빌드 스크립트를 못 바꾸므로 **빌드 단계**에서 후보 코드가
  실행되지는 않는다. 그러나 **Simulator 앱은 Mac의 일반 사용자 프로세스로 실행돼
  Mac 파일·네트워크에 접근할 수 있으므로, 앱 샌드박스를 보안 경계로 보지 않는다.**
  후보 실행 전 안전장치는 아래 "후보 자동 위험 검사"를 따른다.
- **후보 자동 위험 검사 (사용자 결정: 자동 검사 후 실행, 사람 검토 단계 없음).**
  - 후보 diff가 원본에 없던 위험 기능을 새로 넣으면 빌드·실행 전에 자동으로 거절하고
    `blocked_risky_change`로 기록한다. 이 결과는 `verified`가 될 수 없다.
  - 위험 기능은 최소한 다음을 포함한다(설계자 판단, 목록 확장은 빌더 재량).
    - 네트워크: `URLSession`, `Network`/`NWConnection`, socket, `CFNetwork`, 웹뷰 URL
      로드, 새 URL·호스트 문자열.
    - 앱 컨테이너 밖 파일 접근: 절대 경로, 홈 디렉터리 경로.
    - 프로세스·동적 로딩: `Process`/`NSTask`, `posix_spawn`, `system`, `dlopen`.
    - 새 `import`·프레임워크 링크.
    - Objective-C runtime 조작(swizzling 등).
  - 기존 코드에 이미 있던 사용은 막지 않는다. "새로 생긴 것"만 본다.
  - 검사는 diff 기반 정적 검사다. 문자열 난독화 등으로 우회할 수 있으므로 리포트와
    문서에 "위험 코드를 모두 잡는다는 보장이 아니다"를 명시한다.
  - 거절 사유는 해당 파일·줄과 함께 사람이 읽을 수 있게 보여 준다. 거절된 후보를
    사람이 보고 실행하겠다고 고르는 우회 버튼은 간편 모드에 두지 않는다.
- Claude CLI는 파일 읽기·편집 도구만 쓰게 하고, 셸 실행·네트워크 도구와 사용자의
  MCP·플러그인 설정을 쓰지 않는 격리 설정으로 실행한다. (설계자 판단)
- 원본에서 이미 실패하는 기존 테스트는 기준선으로 기록해 판정에서 빼고 리포트에
  표시한다. 후보는 원본에서 통과한 테스트를 모두 통과해야 한다. (설계자 판단)
- 같은 후보 diff를 Claude 재호출 없이 다시 검증하는 기능을 둔다. 수용 기준 5의 로컬·
  공유 모드 비교는 같은 diff로 한다. Claude 출력은 실행마다 달라 비교 기준이 될 수
  없기 때문이다. (설계자 판단)
- 후보는 같은 녹화로 3회 실행하고, `init`에서 지정한 기존 테스트 scheme을 실행한다.
- Claude 수정 시도 횟수 한도와 비용 한도는 설정 파일에 기본값을 두고 실행 결과에
  기록한다.
- 결과물은 검증된 diff와 리포트다. 회사 저장소에는 아무것도 쓰지 않는다.

### 승인 축소 (사용자 결정 + 설계자 판단)

- **사용자 결정:** 승인 단계가 많으면 실패다.
- **설계자 판단 — 간편 모드:**
  - QA가 버그 지점을 지정하고 저장하면 그 녹화가 바로 재현 기준이 된다. 별도
    maintainer 승인은 없다. 저장된 기준은 수정할 수 없고, 바꾸려면 새 녹화나 새
    기준으로 저장한다.
  - Claude 전송 동의는 프로젝트 설정에서 1회 받는다.
  - 해시 고정·환경 점검은 툴이 자동으로 수행하고, 실패할 때만 사람에게 보인다.
- **간편 모드에서도 유지하는 원칙:**
  - 원본 녹화와 저장된 기준은 불변이다.
  - 모든 실행 결과를 센다. 성공한 실행만 고르지 않는다.
  - AI 수정 범위 밖의 변경은 거절한다.
- 엄격 모드는 지금의 revision·digest 승인 흐름을 그대로 쓴다. 프로젝트별로 선택한다.

### 원본 빌드 식별 (설계자 판단)

- 이슈는 녹화에 쓴 빌드의 git commit SHA, 설정 파일 digest, 빌드 산출물 digest에
  묶는다.
- 커밋되지 않은 변경이 있는 상태에서 만든 빌드는 이슈에 "작업 중 소스"로 표시하고,
  변경 diff를 이슈에 함께 저장해 개발자가 같은 상태를 다시 만들 수 있게 한다.
- 개발자의 "재현"은 같은 commit(+저장된 diff)에서 녹화용 빌드를 다시 만들어 실행한다.
  다시 만든 빌드는 원본과 소스·설정 digest가 같아야 한다.
- 로컬 모드에서 이슈를 다른 Mac으로 넘길 때는 파일 내보내기·가져오기를 쓴다.
### QA 녹화용 빌드 배포 (사용자 답 + 설계자 판단)

- **사용자 답:** QA Mac에는 소스와 Xcode가 없다.
- **설계자 판단:** 녹화용 빌드는 개발자 Mac이나 회사 CI에서 툴이 만든다.
  - Simulator용 `.app`: 공유 모드의 공용 Mac으로 보낸다. QA는 브라우저로 조작한다.
  - iPhone용 IPA: 회사가 이미 쓰는 내부 배포 채널(TestFlight 내부 테스트, ad hoc
    등)로 QA iPhone에 배포한다. 툴은 IPA와 배포 안내만 만들고 배포 채널 계정은 다루지
    않는다.
- 녹화용 빌드에는 빌드 식별 정보(commit SHA, 설정 digest, 빌드 digest)를 넣고, QA가
  만든 녹화는 이 정보로 원본 빌드에 묶인다.
- QA iPhone에서 직접 터치로 녹화한 기록은 앱 안의 녹화 화면에서 보낸다.
  - 최소 지원: iOS 공유 시트(AirDrop·파일)로 내보낸 뒤 브라우저에서 coordinator에
    올린다.
  - 앱에서 coordinator로 바로 올리는 방식은 빌더 재량이다. 하려면 짧은 코드나 QR로
    기기를 한 번 연결하고, 앱 안에 장기 credential을 남기지 않는다.
- 이 iPhone 경로는 이번 승인 범위에서 실기기로 검증하지 않는다(5장 수용 기준 7).

### 공유 모드 (설계자 판단)

- 소스·빌드·Claude 실행은 **개발자 자기 Mac**에서 한다. 공용 Mac은 기기를 연결하고
  실행만 맡는다. 회사 소스를 공용 Mac이나 coordinator로 보내지 않는다.
- 빌드 산출물(`.app`)을 공용 Mac으로 보낸다. 기존 원격 전송 한도(64 MiB)는 실무 앱
  규모에 맞게 간편 모드에서 늘린다.
- 공용 Mac에 꽂힌 물리 iPhone은 회사 개발 팀에 한 번 등록해 두는 것을 전제로 한다.
  이 등록은 초기 설정 문서에 안내한다.
- 툴에 등록하는 물리 iPhone은 **테스트 전용 기기**로 취급한다. 등록할 때 "이 기기에서
  대상 앱의 데이터는 매 실행마다 지워진다"를 한 번 확인받는다. 그 앱 이외의 기기
  데이터는 건드리지 않는다. 재설치만으로 Keychain이 지워지지 않는다는 점은 시작
  조건의 한계로 리포트에 표시한다.
- Wikipedia를 실기기에서 돌릴 때는 검증용 사본에서 bundle id·팀·entitlement를
  우리 팀 값으로 바꾼다. 이는 공개 앱 사본에 대한 변경이고 회사 앱에는 적용하지 않는다.
- 기존 coordinator·역할·일회용 호스트 등록·TLS를 쓴다.
- 간편 모드에서는 기기가 꽂힌 Mac을 등록하는 과정을 명령 한두 개로 줄인다.
- QA 역할도 자기 녹화의 기준을 저장할 수 있게 한다(위 승인 축소와 같은 규칙).
