# 일반 앱 이슈 기록과 재현

등록한 UIKit 또는 Android Views 앱에서 시작 조건을 준비한 뒤, 영상과 실행 가능한
행동을 같은 원본에 남긴다. 일반 서비스의 이슈 화면과 `reproof live-issues`가
같은 API를 사용한다. 앱 등록은 [설치 안내](INSTALLATION.md),
[UIKit 관찰](IOS-APP-OBSERVATIONS.md), [Views 관찰](ANDROID-APP-OBSERVATIONS.md)을 따른다.

## 작업 흐름

1. 프로젝트·앱·빌드·기기를 선택하고 등록된 시작 조건을 준비한다. 준비하지 않을
   때는 시작 상태를 모른다는 선택을 명시한다.
2. 기기 화면에서 문제를 재현한다. 이슈가 가진 현재 조작권으로 행동을 기록한다.
   다른 조작자가 권한을 가져가면 이전 조작권의 입력은 거절한다.
3. 녹화를 종료한다. 허용된 자동 앱 로그는 종료 장벽 전에 마지막으로 수집하므로
   로그 패널을 따로 열 필요가 없다. 장벽 이후 새 행동이나 관찰을 원본에 넣지 않는다.
4. 원본의 행동·대기·조건·관찰 기준을 검토하고 명세를 승인한다. 준비 상태를 모르는
   원본에 알려진 상태의 fixture 동등성을 사후에 만들어 넣지 않는다.
5. 승인한 같은 원본 명세를 세 번 재현한다. 수정 제안은 원본과 소스·빌드·진단에
   연결하며, 후보 검증은 [보호 수정 경로](PROJECT-REPAIR.md)를 사용한다.

읽기 권한의 화면 조회는 조작권 수명을 연장하지 않는다. 조작 클라이언트는
`POST /api/sessions/{id}/heartbeat`에 자신의 `clientId`를 보내 세션을 유지한다.
유휴 종료 후에는 이미 동결된 원본으로 이슈의 기기·fixture 정리를 마무리한다.
원본의 불완전 상태를 성공으로 바꾸지 않는다.
종료 요청은 새 입력을 즉시 차단하고 이미 받은 프레임의 저장을 최대 1초 기다린다.
저장 실패나 시간 초과는 원본의 불완전 사유로 남긴다.

## 영상과 시각

일반 서비스의 `Lab.create_video_sink()`는 `transient-spool-v2`와
`VideoLimits.recording_profile()`을 기본으로 사용한다. 허용된 원본 프레임을
일시 저장하고, 영속 MP4 또는 명시적인 손실 증거가 확정된 뒤 원본 프레임 바이트를
정리한다. 원본에는 각 프레임의 순서와 digest, 영상·손실의 연결이 남는다.
이 모드의 이슈 패키지는 정리된 프레임 바이트를 다시 요구하지 않는다.

영상은 H.264 MP4의 연속 구간이며 실제 취득 시각 간격을 유지한다. Android helper는
약 15 fps, iOS helper는 약 5 fps의 취득을 시도한다. 기기 부하에 따라 낮아질 수 있고
일정한 FPS나 모든 디스플레이 프레임의 수집을 보장하지 않는다. 네이티브의 시작·종료
단조 시각을 측정된 호스트 시계 구간에 매핑하며, 재시작·잘못된 시각·누락을 숨기지 않는다.
네이티브 버퍼는 최대 16개 프레임·12 MiB이고 빠진 취득 번호는 손실 구간으로 남긴다.

앱 진단의 `elapsedMs`는 별도 앱 시계다. 영상 시각으로 변환했다고 표시하지 않는다.
[진단 연결](PROJECT-DIAGNOSTICS.md)의 `app-elapsed-unmapped` 표시를 유지한다.

| 한도 | 일반 서비스 기본값 |
| --- | --- |
| 녹화 길이 | G2 녹화 시작부터 최대 600초, 준비 시간 제외 |
| 영상 구간 | 최대 10초·256개 프레임·16 MiB 압축 입력, 총 128개 구간 |
| 결과 영상 | 구간당 최대 32 MiB, 전체 최대 128 MiB |
| 인코딩 설정 | 목표 1.2 Mbit/s, key frame 간격 최대 30개 프레임 |
| 원본 취득 기록 | 최대 10,000개 |
| manifest / 손실 | 최대 8 MiB / 512개 손실 항목 |
| 이슈 패키지 | 압축 archive 256 MiB, 압축 해제 합계 320 MiB |

600초가 되면 새 행동과 범위를 벗어난 프레임을 받지 않고 마지막 로그 수집·영상
확정·기기와 fixture 정리를 진행한다. 이미 보낸 입력의 응답은 실제 도착 시각과
결과를 유지한다. 인코딩 실패·손실·정리 불명확 상태는 별도로 남으며, 600초에 도달한
사실만으로 완전한 영상이나 성공 판정을 만들지 않는다.

## 용량과 중단 복구

일반 서비스의 공유 증거 예산은 1 GiB다. 기존 512 MiB 저장소는 신뢰된 로컬 서비스
구성에서만 양의 용량 확장을 허용하며, 기존 예약 ID·상태·청구를 보존한다.
일반 `DiskBudget` 생성자는 다른 설정이나 용량을 자동으로 바꾸지 않는다.
명시적으로 작은 예산을 선택하면 시작 전에 필요한 예약이 거절될 수 있다.

프로젝트를 다시 등록하면 같은 프로젝트에 속한 중단된 영상 설정과 종료된 녹화를
복구한다. 복구는 저장된 취득·영상 저널을 사용하며 기기 실행이나 새 입력을 시작하지
않는다. 설정 도중 중단되어도 실제 비어 있음이 확인된 저장 공간만 반환한다.
알 수 없는 파일·동작·정리 결과는 보존하고 실패를 표시한다.

원본이 만료되면 원본 조회는 중단한다. 아직 정리하지 못한 임시 프레임의 증거만
정리가 확정될 때까지 유지하고, 그 뒤 삭제한다. 동결된 원본의 digest나 결과를
수정하지 않는다. 이전 원본 프레임 보관 방식과 schema 1 영상은 계속 읽을 수 있다.

## 검증 범위

[D3 검증 기록](../artifacts/product-delivery/d3-issue-flow-r1/acceptance.json)에 다음 범위를 연결했다.

- 최종 wheel의 일반 서비스·CLI: 전용 Android 에뮬레이터에서 476개 프레임을 기록하고
  시작 조건·자동 로그·같은 원본 3회 재현·로컬 제안·진단과 패키지 내보내기를 확인했다.
- 별도 실제 10분 녹화: 600,000ms 자동 종료, 8,743개 프레임·60개 구간·손실 0개,
  모든 프레임의 독립 디코딩과 PTS 일치를 확인했다. 이 실행의 후속 스크립트 오류는
  보존했으며 10분 원본의 재생까지 완료한 것으로 표시하지 않는다.
- 설치된 UI: 실제 영상 재생·행동 시점 이동·3회 재현 결과·패치 검토와 로그아웃 정리를
  1440px 및 390px 폭에서 확인했다. UI 검증 실행의 진단 hook과 대기 시간 초과는
  최종 일반 CLI 실행과 구분해 기록했다.
- 실제 iOS Simulator: 네이티브 시각·자동 클릭 로그·실제 MP4 26개 프레임·독립 디코딩을
  확인했다. 준비 조건 없는 관찰 프로필의 원본은 `frozen-incomplete`를 유지했다.
  새 Simulator의 XCTest 시작은 기존 15초보다 길 수 있어, 원래 권한을 계속 확인하는
  최대 90초의 제한된 대기를 사용한다.

Python 검사는 고유 1,259개 ID의 근거를 연결했다. 전체 실행의 두 실패는 실행 경로와
예전 테스트 예산을 바로잡은 개별 재검사로 해결했으며, 실패한 전체 로그도 보존했다.
회사 앱·승인된 외부 AI·물리 기기·서로 다른 두 Mac과 전체 iOS 이슈/수정 흐름의
수용 검사는 별도로 남아 있다.

D4 전체 회귀에서 원격 worker의 최신 프레임 polling 경로도 보완했다. worker의
프레임 순번이 건너뛰면 정확한 누락 구간을 기록하고 다음 프레임을 계속 보존한다.
누락이나 원격 취득 시각을 채워 넣지 않으며 원본의 불완전 표시는 유지한다.

같은 원본의 반복 재생에서는 이전 정리가 확인된 다음, coordinator가 worker의
최신 소유권 보고를 받기까지 최대 15초 기다린다. 오래된 예약 보고 때문에 다음
시도를 즉시 실패시키지 않는다. 이 대기는 기기나 inventory 상태를 변경하지 않고,
기존 권한·취소·기한을 다시 확인한다. 로컬 quarantine을 우회하지 않는다.

[D4 전체 회귀 기록](../artifacts/product-delivery/d4-protected-adapters-r1/full-suite-test-ids-r3.json)에
고유 1,511개 검사의 통과를 연결했다. 실제 worker 두 개, coordinator 재시작과 원본
3회 재현·패키지·브라우저 검사는 소유한 합성 환경이며 회사·두 Mac 수용과 구분한다.
